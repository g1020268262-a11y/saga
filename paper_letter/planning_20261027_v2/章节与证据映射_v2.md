## 2. 性质与观测量的对应

### P1：策略求值一致性

**定义与可否定性。** 期望实际求值与参考求值一致；一个语义明确的配置就足以构成反例。本文选择唯一较具体拒绝规则与一般允许规则，避免将同等优先级的未定义决策引入论证。

**直接观察。** 身份 `alice@example.com:agent`；规则 `alice@example.com:* → -1` 与 `* → 10`。具体拒绝在前时实际返回 10，交换规则次序后返回 -1。根因在 `match()` 对 `best_pattern` 的维护。

**传播观察。** 成功消费者归档的 `summary.txt` 记录完成及三组预期满足；`cases/da/result.json`、`events.jsonl` 支持传播至 OTK 释放、消费和 ACT 签发、存储。A/A、D/A、D/D 指参考决定／实现观察。应用消息接受未执行。

**编写方式。** 第 3 章给判定表达式与抽象范围，第 4.1 节给具体输入、实际结果和终点。不把旧 bridge 中固定场景的 `ChatAccept` 轨迹附会成这次原生执行的后续步骤。

### P2：OTK 发放／使用对应

**正文事件与实际事件。** 大纲中的 `Issue(A,C,k)` 对应 Tamarin 的 `ProviderIssue(A,C,k)`；`Use(A,C,k)` 是 `RequestAccepted(A,C,k,t,pac)` 对 k 的投影。正常路径与对应凭证检查要求先有 `ReceiverTokenIssued` 和 `ClientDecryptedToken`，因此成功使用包含获取及解密新 ACT 后的模型请求接受。

| 需要的结果 | 已有 lemma | 主配置与对照 |
|---|---|---|
| 原有发放上限 | `provider_per_sender_issuance_limit` | 允许转交时成立；这不是受反例推翻的目标 |
| 成功使用应对应同一发送方领取 | `successful_use_requires_issue_to_same_sender` | 允许转交时反例；禁止转交时成立 |
| C 额度耗尽后通过转交继续完成流程 | `transfer_after_C_exhaustion_completes` | 允许转交可达；禁止转交不可达 |
| 正常 C 流程保持可执行 | `normal_C_completes` | 两种主要配置均可达，排除对照通过阻断全部流程而空成立 |
| 单个 OTK 只消费一次 | `receiver_consumes_each_OTK_once` | 允许转交仍成立；用于解释转交与重用的区别 |

当前配置中每方一个领取额度、总共两个 OTK、策略静态允许；C 成功使用两个不同 OTK。对应数量结论仅在这一配置下陈述。模型每枚 ACT 只观察一次应用请求，不负责本稿的 ACT 重用或配额竞争分析。

**编写方式。** 第 3 章区分原有发放性质与新增同人对应性质；第 4.2 节解释它们为何会有不同结果。原始模型的多条 sanity lemmas 不必逐条挤入主文，也不把三配置十查询的运行数量作为贡献。

### P3：ACT 累计准入上限

**模型量。** `ReceiverQuotaSafety == Accepted <= InitialQuota`；`Accepted` 是模型中的累计准入。检查余额非负不能替代此性质。

**有限反例。** 配额归档的 `concurrent_race` 在无故障配置中报告该 invariant 被违反，保存 13 个状态的反例；终点两连接均已准入，调用计数尚不能等同于真实业务完成。`normal_single` 是独立正常对照。

**原生方法量。** `qmax-20261020/results.json` 中，串行对照为额度 50、提交 51、计数后端调用 50；并发实验为 49 次串行调用后，两连接先通过最后额度检查，最终调用 51、余额 0，保存三次重复。该计数是方法调用量，与模型的准入计数分别报告。

**编写方式。** 第 3 章保留检查／扣减的非原子结构，第 4.3 节先解释最小交错，再分别报告两种观察。交付模型的 manifest 记录 `native_replay_performed=false`、`repair_implemented=false`；不能将方法级实验写成已重放所有交付反例，不能报告不存在的修复验证。

## 3. 正文与 artifact 的分配

**主文必须能独立解释核心论证。** 三项性质、关键状态、最小配置、主要见证、正常对照及结论条件留在正文。读者不应必须打开 artifact 才能明白为什么两次使用仍符合一次发放预算，或为什么余额为零仍能超额准入。

完整源码映射、工具版本、命令、全部 lemma、原始轨迹、运行时和哈希保存在 artifact。原有成功归档作为证据来源；旧失败运行、原 ProVerif 覆盖诊断和其他故障计账候选不扩充为本稿新贡献。
