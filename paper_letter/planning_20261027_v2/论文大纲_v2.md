编制日期：2026-10-27。本文重排研究叙事与章节职责，保留既定的三项研究结果及 policy → OTK → ACT/token 顺序。旧大纲保留于 `planning_20261026/`；本轮不修改论文正文、模型或证明记录。

## 一、论文的中心问题

**本文研究 SAGA 中策略、凭证发放和请求配额三个环节的执行保证，以及这些保证的适用范围。**

推荐工作标题：**Formal Analysis of Policy and Quota Enforcement in SAGA**。

中文：**SAGA 中策略与配额执行的形式化分析**。

论文从同一条授权流程提出三个研究问题：

- **RQ1：策略判定是否符合所配置规则的优先语义？** 检查 matcher 的具体求值能否正确落实规则选择。
- **RQ2：OTK 发放上限能否进一步保证领取者与使用者对应？** 区分 Provider 实际约束的数量和本次提出的更强使用目标。
- **RQ3：ACT 的请求额度能否在并发连接下约束累计准入？** 检查配额验证与扣减之间的交错。

三项贡献回答上述问题：识别策略求值的实现分歧并观察其凭证签发影响；在保留 OTK 发放上限的模型中展示转交造成的使用关系差别；通过有限状态反例及受控原生方法调用分析 ACT 超额准入机制。工具用于支撑这些结果，不另列“采用多工具”为贡献。

### 2. SAGA Protocol and Threat Model｜协议与威胁模型

**中心句：理解三个研究问题所需的共同背景，是发送方经过 Provider 领取 OTK，再与接收方建立 ACT 并提交受额度约束的请求。**

#### 2.1 Authorization Workflow｜授权流程

统一参与方：P 为 Provider，A 为接收方，B、C 为已登记发送方。统一对象：`CP_A` 为接触策略，k 为 A 的 OTK 公钥，t 为接收方签发的 ACT。OTK 的私钥由 A 保存；ACT 是后续请求凭证。

正文配一张必要流程图，依次展示：

1. P 根据实际申请者身份执行策略判定，并检查对该发送方的 OTK 发放额度。
2. P 发放 OTK；发送方使用自己的身份及材料向 A 请求 ACT。
3. A 再检查实际连接者的本地策略，核验并消费 OTK，通过密钥交换签发 ACT。
4. 后续请求执行 ACT 有效性和额度检查，然后扣减额度。

图中保留两端策略检查的真实位置。章节顺序 policy → OTK → ACT 并不意味着协议里只有一次 policy 检查。B→C 的转交可作为侧向箭头标记；不要把三项问题画成一条必须连续发生的攻击链。

#### 2.2 Threat Model and Assumptions｜威胁模型与假设

**本稿按研究问题声明攻击行为和运行条件，不预设一种覆盖所有证据的万能攻击者。**

| 分析场景 | 允许的行为或配置 | 必须写明的条件 |
|---|---|---|
| policy | 用户合法配置两条同时匹配的规则，观察同一请求的规则选择 | 不假设攻击者可修改接收方策略；注册与 TLS 在受控消费者执行中由 fixtures 给定 |
| OTK | 获准的 B 主动把尚未使用的 OTK 交给同样获准的 C | 固定 A/B/C、两个 OTK、B/C 各一个领取额度；理想 mTLS；静态策略；不泄露长期私钥 |
| ACT | 有效 token 持有者并发提交多个连接上的请求 | 保留真实检查／扣减之间的间隙；模型配置与原生方法实验分别报告；字节传输和计数后端有替代 |

本节只介绍理解模型所必需的假设。完整密码算法、注册流程、长期密钥生命周期和所有网络故障不在本文统一覆盖范围内。

### 3. Analysis Models and Security Properties｜分析模型与安全性质

**中心句：三项分析共享协议术语，但分别保留规则选择、OTK 状态及配额交错所需的结构。**

#### 3.1 Models and Abstractions｜模型与抽象

**这一节解释如何从机制得到分析对象，而不是介绍各个验证工具的通用功能。**

按 policy → OTK → ACT 各用一段交代模型。

**策略求值。** 用独立的规则优先语义定义参考结果，以实际 matcher 作为被检查的实现。最小反例只需要一个唯一较具体的匹配规则和一个一般匹配规则。说明本项是规则语义与代码求值的可执行对照，已有证据并非一项 Tamarin 或 ProVerif 策略定理。

**OTK 交互。** 用 Tamarin 表达 Provider 的可发放 OTK、接收方尚未消费的 OTK、按发送方持有的领取 credit，以及领取、转交、ACT 签发、解密和请求接受事件。Provider 与接收方的 OTK 状态分别表示，避免把发放和消费错误地合并。转交是一条显式行为；发送方继续以自己的 PAC 和身份取得 ACT。

**ACT 配额。** 用 TLA+ 表达共享余额、各连接的局部执行位置及累计准入计数。`Check` 与 `Debit` 必须分别成为可交错步骤；已有模型中余额下限为零的更新也保留。模型的有限初始额度与连接数明确给出。原生方法实验用于检查同类交错机制，不作为源码与模型等价性的证明。

本节保留“状态／事件对应哪一项机制”的简短说明。源码行号、完整规则、配置文件与工具命令进入随附 artifact。不要在本文声称已经有一个统一源规格，能够自动导出全部模型并跨工具复用证明。

#### 3.2 Security Properties｜安全性质

**每项结果都先有明确的检查目标，且目标中的计数和身份不能混用。**

**P1：策略求值一致性。** 在参考语义已确定优先规则的配置内，要求实际求值与参考求值一致：

\[
  \operatorname{Eval}_{impl}(CP_A,C)
  =\operatorname{Eval}_{spec}(CP_A,C).
\]

本项可以由一个有效配置反例否定，不需要把少量对照写成“所有策略均已验证”。正文可直接给出选定配置中的 -1 与 10。

**P2：OTK 发放／使用对应。** 先陈述被保留的原有发放约束：

\[
 I(A,C)\le B^{OTK}_{A,C}.
\]

再明确提出更强的候选关系：若 C 成功使用 k，则此前应有 P 将同一个 k 发给 C 的事件：

\[
 \mathsf{Use}(A,C,k)@i
 \Rightarrow \exists j<i:\mathsf{Issue}(A,C,k)@j.
\]

`Use` 在本模型中对应 ACT 已签发、发送方已解密后发生的请求接受，不只是一次请求尝试。现有模型中 `B^{OTK}_{A,C}=1`；不同 OTK 的成功使用数量记为 `U(A,C)`。发放约束和候选关系分别检查，不能把后者直接说成 SAGA 原文已承诺的预算定义。

**P3：ACT 累计准入上限。** 对初始额度为 `Q_t` 的 ACT t，检查所有可达状态是否满足：

\[
 N_{admit}(t)\le Q_t.
\]

`N_admit` 是接收方累计准入次数。余额非负是另一个性质；后端方法调用数和业务完成数也不能代替这个定义。正文解释一次最后额度上的并发交错即可说明差别。

最后简述有效性对照：正常通信应可执行；OTK 发放上限及单次消费仍应成立；禁止转交后，正常 C 路径仍能完成。目的在于排除不正确建模或阻断全部通信造成的假象，不把这些对照另算研究贡献。

### 4. Verification Results and Security Analysis｜验证结果与安全分析

**中心句：三项检查分别暴露策略求值分歧、OTK 发放与使用的条件差别，以及并发准入超过 ACT 初始额度的执行。**

本章开头用表 1 概括第 3 章性质、检查配置及结果，随后按同一顺序解释反例。表格必须保留“在哪里检查”的一列，不能把实现观察与符号模型统一画成同一种证明勾叉。

| 检查目标 | 主要配置 | 结果与证据类型 |
|---|---|---|
| P1：策略求值一致性 | 具体拒绝与一般允许同时匹配 | 真实函数反例；受控消费者执行到 ACT 签发、存储 |
| P2：OTK 发放／使用对应 | 各一个领取额度、允许 B→C 转交 | Tamarin 中发放上限成立，同人使用对应有反例；禁止转交对照保留正常通信 |
| P3：ACT 累计准入上限 | 多连接竞争最后额度 | 有限 TLC 反例；原生方法实验独立观察到同类超额调用机制 |

#### 4.1 Policy Evaluation Inconsistency｜策略求值分歧

**本节解释 P1 的一个具体反例及其影响终点。**

首段给出完整最小输入：同一身份匹配 `alice@example.com:* → -1` 和 `* → 10`。在本次优先语义下应由较具体的拒绝规则决定，实际 matcher 在具体规则在前时返回 10，交换顺序后返回 -1。接着指出根因：选中规则后未更新 `best_pattern`，使后续一般规则仍可覆盖已选结果。

第二段说明为何这不只是函数输出差别：成功归档中的受控 Provider／接收方路径实际到达 OTK 释放、消费及 ACT 签发、存储。允许和拒绝配置提供对照。用一行交代 TLS、注册与传输替代环境，并注明没有执行应用消息接受。

本节结尾回答 RQ1：已确认的规则求值分歧可以传播到凭证签发。不要把 `D/A` 标签解释成两端门控的拒绝／允许；这里它指规范决定与实现观察。

本节不重新讲解全套策略语言，不展开旧 bridge 工程，也不把条件性 ProVerif 轨迹与上述原生代码执行合并。

#### 4.2 OTK Issuance and Use｜OTK 发放与使用

**本节同时报告发放上限成立和更强使用关系失败。**

首段对照第 3.2 节说明：每发送方一个领取额度的配置中，Provider 的发放限制得到保留；每个 OTK 在接收方仍只消费一次。因而本节分析的重点是已经领取的材料能否被别的已授权身份使用。

第二段给出一个按事件顺序压缩的见证：C 用自己的 OTK 完成正常流程 → C 因额度耗尽被 Provider 拒绝再次领取 → B 把另一枚已领取且尚未使用的 OTK 交给 C → C 以自己的身份、PAC 和密钥材料取得新 ACT，并完成另一次模型中的请求。B 的原始领取发生在其转交之前，不必把它强制安排在 C 被拒绝之后。

第三段解释结果：固定配置中 `I(A,C)≤1` 与 `U(A,C)=2` 可以同时出现；没有需要冒充 B 或转交 B 已有 ACT 的步骤。禁止转交后，相同的正常 C 路径仍可达，而对应性质成立。把存在性见证与正常路径检查一起报告，避免读者将反例理解为简单破坏认证。

本节结尾回答 RQ2：发放预算本身不足以推出同人使用关系，是否要求后者需要明确为额外目标。结果当前来自所列符号模型，没有原生网络转交重放。原论文 C4 已涉及恶意 Agent 共享访问控制材料，不能将研究缺口描述为“原文完全未考虑共享”。

#### 4.3 Concurrent ACT Quota Enforcement｜ACT 配额的并发执行

**本节解释为什么余额保持非负仍可能违反 P3。**

首段用最小交错解释模型机制：余额为 1；连接 1 检查通过；连接 2 也检查通过；二者再分别扣减。由于扣减以零为下限，最后余额为 0，但已有两次准入。该段必须对上第 3.1 节分离的检查与扣减步骤。

第二段报告 TLC 在无故障并发配置下找到 `ReceiverQuotaSafety` 反例。说明其性质计数的是准入，反例终点没有要求后端调用或业务完成；本项是有限配置的反例，不是所有并发配置的正确性结论。

第三段报告独立的原生方法观察：初始额度为 50 时，串行 51 次提交产生 50 次计数后端调用；49 次串行后让两个连接都完成最后额度检查，总调用为 51、余额为 0，保存的三次受控重复一致。交代使用真实方法与本地凭证检查，但传输、证书发现和计数后端存在替代。

本节结尾回答 RQ3：当前检查／扣减分离允许超额准入；方法级观察支持相同机制。不要将两类证据改写为已经重放了同一条完整网络轨迹，也不将计数后端说成真实 LLM 服务。

### 5. Discussion and Conclusion｜讨论与结论

**中心句：三个结果分别对应规则选择、材料使用对象和共享配额状态的执行义务。**

第一段提炼设计含义：策略选择需要符合优先语义；若系统要求实际使用绑定到领取身份，就需要相应绑定检查；ACT 配额检查与扣减需要共同维护准入上限。三者是从结果得到的设计方向，目前没有统一修复实现或修复后联合验证。

第二段用最短篇幅说明结论范围并收束：本研究给出固定版本、配置及证据条件下的三个结果；并未证明完整 SAGA，也未证明三项问题能串联成一条部署攻击。分别构建的模型共享术语，不构成已经证明精化关系的整体系统。

本章不另开长“威胁有效性”清单。影响各项结果的关键条件应已在前文相应位置交代，此处只概括共同限制。
