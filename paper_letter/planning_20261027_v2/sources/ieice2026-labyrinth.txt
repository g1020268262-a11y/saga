Kakeru WATANABE†∗, Nonmember and Kazuki YONEYAMA†a), Member
SUMMARY Messenger, a messaging service, is widely used in the
United States and around the world, with 947 million monthly active users
as of February 2025. In December 2023, a default implementation of end-to-
end encryption in Messenger and two accompanying technical white papers
were released. Labyrinth Encrypted Message Storage Protocol is one of
the protocols presented in these technical white papers and is intended
to securely share message history between devices associated with each
Messenger account. However, there has been no rigorous discussion of
the security of Labyrinth to date, and the security model claimed in the
technical white paper has some ambiguity. In this paper, we give the first
formal verification of Labyrinth. First, we verify the confidentiality and
integrity of the stored messages as the security claim in the specification
(i.e., only considering outside adversaries). Next, considering the case of a
device that has been revoked from an account and abused, we exhaustively
verify under what conditions it is possible to break the confidentiality and
integrity of a message. As a result of the verification, we clarify the
conditions under which the confidentiality and integrity of stored messages
can be broken by abusing a revoked device and the specific procedures for
doing so while satisfying all the security claims made by the specification.
key words: formal methods, Labyrinth, Messenger, storage protocol
1. Introduction
1.1 Background
Social networking services (SNS) and other communica-
tion services are widely used, and ensuring their security
is an important issue. Meta’s Messenger [2] is estimated
to have 947 million monthly active users as of February
2025, which is the fourth largest number in the world among
messenger applications after WhatsApp [3], WeChat [4],
and Telegram [5] and widely used internationally [6]. In
December 2023, Meta announced the introduction of end-
to-end encryption (E2EE) in Messenger as a standard for all
users [7], and in conjunction with this announcement, pub-
lished the specifications for the following two protocols: the
core cryptographic protocol for transmitting messages be-
tween clients [8] and the protocol for end-to-end encrypting
stored messaging history between devices on a user’s account
(Labyrinth Encrypted Message Storage Protocol) [9]. These
two protocols have already begun to be used in Messenger at
the time of this writing∗∗∗, but no rigorous proof of security

In the past, handwritten security proofs were used to
show the security of cryptographic protocols, but in recent
years, verification using formal methods has been gaining
popularity. The main advantages of formal verification are
the automation of verification and the prevention of human
error. By mathematically expressing the specifications to be
verified and the security to be satisfied, the verification work
itself can be delegated to a computer. Another advantage
is that the verification itself does not have to be considered
from scratch every time a minor setting is changed. The user
only needs to consider how to change the input since the
verification content passed to the computer as input can be
reused, and security verification can be left to the computer.
With the above background, we examine the security of
Labyrinth using formal methods in this paper.
1.2 Related Work and Motivating Problem
There are various known security verifications of crypto-
graphic protocols using formal methods and security analysis
of E2EE in SNS.

Formal methods are widely used for the security verifica-

1.2.3 Limitation on Security Requirements of Labyrinth
The Labyrinth specification [9] proposes several design goals
in terms of Messenger as ‘a product and privacy’. In
Labyrinth, the concept of epoch is also defined to take into
account cases where a device is revoked from an account.
The epoch is renewed when one device is revoked, and it
is guaranteed that messages stored in a new epoch cannot
be decrypted using keys and other data handled in previous
epochs. The listed design goals do not consider the case of
attacks using revoked devices. Hence, we consider that the
security claimed in the specification alone is only for limited
cases and it is significant to consider what threats can be ap-
peared by the misuse of revoked devices and the information
they hold†.

Labyrinth. For security verification, we use ProVerif [11],
a generic verification tool for cryptographic protocols, be-

tion with the ProVerif language. In formalizing the proto-
col specification, we have identified ambiguities within the
specification regarding the methods for sharing confidential
information, and the specific composition and usage of its
constituent components. We address such ambiguities by
Encryption Ver. 1.0 [18], which differs from the current specifica-
tion [19].

1.4 Our Key Technique for Formalization
Labyrinth is a stateful protocol where devices can be added or
revoked at any time without limit, as it is a protocol to ensure
security in the storage of messages in a single account. On the
other hand, while ProVerif has the advantage of being able
to express cryptographic protocol specifications in a more
natural way, it does not support stateful protocol descriptions.
We focused on the fact that all epochs in Labyrinth are linked
in a chain, taking over information from previous epochs,
and formalized and verified with ProVerif based on a specific
pattern of events that can occur when there is only one device
connected to an account. In the formalization using ProVerif,
the situation of epochs defined in Labyrinth is realized using
the phase command, and the messages stored in each epoch
are formalized as being stored in the database across epochs
by using table. Based on these assumptions, the behavior
of each entity is formalized as a sub-process, and in the case

2. Labyrinth
In this section, we give a cryptographic description of the
Labyrinth protocol’s structure based on the technical white
paper published by Meta [9]. Although the protocol in the
white paper is described with the natural language, we orga-
nize the protocol algorithmically as a common manner for
the cryptographic protocols.
2.1 Cryptographic Primitives (and its Concrete Specifica-
tions)
2.1.1 Authenticated Symmetric Encryption (AES-GCM-
Extended)
Labyrinth uses an extension of AES-GCM [28] named AES-
GCM-Extended. The syntax used in the protocol description
is as follows:
ciphertext ← encrypt(key, aad, plaintext)
plaintext ← decrypt(key, aad, ciphertext)
where aad is additional authenticated data. The concrete
construction of AES-GCM-Extended is given as follows: It
takes a 32-byte key and a 28-byte nonce, and from these, it
generates a subkey and subnonce as follows.
subkey := hchacha20(nonce[0 : 16], key)
subnonce := nonce[16 : 28]
Then, subkey and subnonce are used within AES-GCM-
256 to encrypt and decrypt the data.
2.1.2 Public Key Encryption (Labyrinth HPKE)
Labyrinth uses an authenticated public key cryptosystem
named Labyrinth HPKE (Hybrid Public Key Encryption).
The syntax used in the protocol description is as follows:
(priv key enc, pub key enc) ← pk enc keygen()
(priv key auth, pub key auth) ← pk auth keygen()
ciphertext ← pk encrypt(pub key enc, pub key auth,
priv key auth, pre shared key, aad, plaintext)
plaintext ← pk decrypt(pub key enc, priv key enc,
pub key auth, pre shared key, aad, ciphertext)
It is required that plaintext cannot be decrypted if
ciphertext is generated with priv key auth not corre-
sponding to pub key auth in decryption. We note that no
concrete decryption algorithm is given in the specification,
whereas a specific encryption algorithm is given. In this
paper, we assume that Labyrinth HPKE is ideally secure†.
2.1.3 Digital Signature (XEdDSA)
Labyrinth uses XEdDSA [29] as a digital signature. The
syntax used in the protocol description is as follows:
(priv key, pub key) ← pk sig keygen()
signature ← pk sign(priv key, use case byte, data)
is valid ← pk verify(pub key, signature,
use case byte, data)
2.1.4 Message Authentication Code (HMAC-SHA256)
Labyrinth uses HMAC-SHA256 [30] as MAC. The syntax
used in the protocol description is as follows††:
mac value ← mac(key, data)
2.1.5 Key Derivation Function (HMAC-SHA256)
Labyrinth also uses HMAC-SHA256 [30] as the key deriva-
tion function. The syntax used in the protocol description is
as follows:

Labyrinth can use any available cryptographically strong

2.1.7 Oblivious Revocable Function
Labyrinth uses Oblivious Revocable Function (ORF) [31].
ORF is a cryptographic primitive used to manage the addition
of a new device by an existing device and the revocation of a
part of devices. The syntax used in the protocol description
is as follows:
client state ← orf client init()
server state ← orf server init()
(new client state, evolve token)
← orf client evolve(client state)
new server state ← orf server evolve
(server state, evolve token)
In Labyrinth, no specific ORF functions are defined other
than those listed above, and no further detailed state ma-
nipulations are defined. In this paper, we formalize and
verify only what is described in the Labyrinth specifica-
tion [9]. It is required that new server state corresponds
to new client state via evolve token. We note that
no concrete algorithm is given in the specification. In this
paper, we assume that the oblivious revocable function is
ideally secure.
2.2 Protocol Overview
Labyrinth is a protocol for secure sharing of message history
between multiple devices owned by the same user in Meta’s
Messenger. Labyrinth has its own goals in terms of product
and privacy.
2.2.1 Entities
The entities that appear in Labyrinth are as follows.
Client: Each device (including virtual devices described in
Sect. 2.3) is defined as a client. A client is associated
with an account, has its own key and access rights to
the epoch, and is responsible for storing and loading
messages.
Server: The server held by Meta manages the access rights
of the devices associated with each account, as well as
the DB for storing and loading messages.
2.2.2 Product Goals
1. Allowing messaging history to be accessed on new de-
vices
2. Providing an efficiently queryable and writeable stor-
age mechanism, so devices need not store their entire
message history.
3. Preventing Meta from accessing data stored in
Labyrinth
2.2.3 Privacy Goals †
Baseline Message Secrecy: Labyrinth is intended to pro-
tect the content of messages from the server side and
all that can monitor communications.
Post-Revocation Message Secrecy: Labyrinth guarantees
that no device removed from the account can subse-
quently decrypt encrypted and stored messages.
Attachment Unlinkability: Labyrinth aims to strongly
guarantee that attachments stored separately from the
mailbox are not linked to the mailbox or messages.
Labyrinth in Messenger: Labyrinth is currently undergo-
ing testing and ongoing development and has not yet
achieved all of the above goals. However, it considers
the secure storage and restore of messages (Baseline
Message Secrecy) to be the most critical objective and
believes this should not be compromised.
2.2.4 Epoch
Epoch is a concept provided for Labyrinth key management,
which is updated only when a device is revoked; within an
epoch, devices can be added an unlimited number of times,
but revocation can occur only once. When the epoch is
updated, the key for message encryption is updated, and it
is no longer possible to decrypt messages in the new epoch
from the revoked device.

The entire protocol flow for the case where two devices
exist and the device added later is revoked is illustrated in
Fig. 1. The calculation and communication in each arrow are

has not been revoked.

3. ProVerif
ProVerif [11] is an automated cryptographic protocol ver-
ification tool that works by defining the specification of a
cryptographic protocol and the security requirements to be
verified. ProVerif verifies cryptographic protocols by ide-
alizing messages sent and received in the communication
channel into symbols. Since the verification in ProVerif is
based on the Dolev-Yao model [32] such that attackers can
read, modify, manipulate data internally, delete, and send
messages. The inputted cryptographic protocol is automati-
cally translated into Horn clauses by the applied pi-calculus,
and the security requirement is verified by whether or not an
event violating the security requirement can be derived.
The security requirements verified using ProVerif in this
paper are confidentiality, integrity, and indistinguishability.
Confidentiality: We can verify whether an attacker can ob-
tain given information using the reachability verifica-
tion (secrecy).
Integrity: The correspondence assertion verification is used
to check whether or not, between entities communicat-
ing using the same credentials (e.g., private key) when
an event of the receiver occurs, an event of the corre-
sponding sender always occurs in advance (falsifiabil-
ity).
Indistinguishability: The observational equivalence verifi-
cation is used to check the equivalence of two processes
(e.g., verifying message privacy by discerning whether
two processes are sending the same message).
4. Our Formalization of Labyrinth Using ProVerif
This section shows an overview of our formalization of
Labyrinth. We use ProVerif 2.05, the latest version of
ProVerif. See [33] for the full ProVerif code of our for-

4.1 Main Idea
As mentioned in Sect. 2.3, Labyrinth is a stateful protocol.
On the other hand, ProVerif does not support stateful pro-
tocol descriptions. However, we find that given that all
epochs are formed by inheriting information from previ-

a device can be generalized and captured. From such an
insight, we formalize Labyrinth by covering the follow-
ing specific flows using ProVerif. In particular, we need
to be mindful of the differences that arise in the way
epochEntropy is shared when updating epochs and the way
epoch information is accessed when adding devices, and we
consider flows that encompass these differences. Note that
the devices in Labyrinth are capable of storing messages at
the latest epoch and reading messages at any epoch at any

4.2 Epoch Updating (Using phase Command)
An epoch update will only occur if the device expires from
Labyrinth. The formalization in this paper uses the phase
command to chronologically manage the execution of flows
in each device sub-process. In ProVerif, the timing of the
start of execution of the main process is phase 0, and then
the phases are specified in order from 1. In this example,
the first epoch is phase 0, and the epoch after the device
expires corresponds to phase 1. Within each device and
server sub-process, phase 1 is specified at the appropriate
time.
4.3 Storing and Loading Messages
All storing and loading of messages occur an arbitrary num-
ber of times at arbitrary timings after the initialization phase
has passed. In the example flow, the sub-process of the
device that exists from the beginning of initialization is for-
malized to store and load messages an arbitrary number of
times in the first epoch. (The symbol ! to execute multiple
processes in parallel is used in the sub-process.) Then, the
sub-process of the device to be added later is formalized so
that it can read and store the message any number of times as
soon as the secret information of the epoch is fetched. Then,
after the device added later expires and the epoch is updated
by the phase to derive a new key, the message at the updated
epoch is expressed to be stored and loaded in the same way.
Note here that it formalizes that the message in one previous
epoch is also read.
Each device sub-process shall publish the message to
the communication channel with the server when storing the
message and shall read the message from the same commu-
nication channel when reading it. On the other hand, the
server sub-process is formalized with care so that each de-
vice at each epoch can store and load messages. Messages
at each epoch are managed by a sub-process of the server
using the table functionality of ProVerif. A table cor-
responding to each epoch is prepared, messages arriving at
the server from each device are inserted into thetable, and
messages are retrieved from the table and sent when each
device reads the messages. By formalizing in this way, the
message of each epoch can be taken over and retained even
if the phase command is used, and the situation where each
device reads the message of a past epoch can be expressed.
Related to Sect. 5.1.2, when each device stores and loads
a message, theevent should be placed with a clear indication
of which device performed the processing for which epoch
of the message.
4.4 Revocation of Devices
The verification in this paper aims to evaluate the security
impact of whether or not an attacker can abuse the infor-
mation of a revoked device. In the case of allowing abuse,
in the sub-process of the device to be revoked, immediately
after updating the phase, disclose the device’s private keys
and recovery codes to a public channel to which the attacker
has access. Given that an attacker can intervene as a man-
in-the-middle in the device registration and epoch update
process, it is possible to attack using information on devices
that have been revoked by having access to recovery codes
and other information. In the case of not allowing, the null
process (0.) shall be executed after updating the phase in
the sub-process of the device to be revoked.

5. Formalization of Security Requirements
5.1 Security of Labyrinth
The formalization of the security requirements considering
the cases in Sect. 4.1 is as follows.
5.1.1 For Confidentiality
The latest epoch is the second epoch, thus, each of the fol-
lowing is verified.
• confidentiality of messages stored in the first epoch
• confidentiality of messages stored in the second epoch
A secret query is used for verification. This allows the
confidentiality of all messages to be verified by storing them
in each device (sub-process in ProVerif) with the same name
symbol.
5.1.2 For Integrity
Integrity is verified by expressing the following events using
correspondence assertions. Here, Client1 is a device that has
existed since Initialization, and Client2 is a device added to
the account during the process and subsequently revoked.
• The message that Client1 and Client2 decrypt as the
message of the first epoch is the message that Client1
and Client2 stored in the first epoch.
• The message that Client1 decrypts as the message of
the second epoch is the message that Client1 stored in
the second epoch.
In order to express these using correspondence assertions,
the sub-processes of each device place events for storing
and loading messages at each epoch as different events. By
formalizing in this way, it is possible to verify that messages
can only be stored and loaded by legitimate devices within
each epoch. Similarly, in other verification patterns, the main
focus is on which devices appear in each epoch.
5.2 Security of AES-GCM-Extended
In the security verification of Labyrinth †, AEAD is formal-
ized as an ideally secure AEAD, rather than as the concrete
scheme in the specification. We verify whether the con-
crete scheme AES-GCM-Extended is as secure as an ideally
secure AEAD.
5.2.1 For Confidentiality
We examine the case that the same plaintext is encrypted

with the same key, nonce, and AAD with each of the ideally
secure AEAD and AES-GCM-Extended, and it is verified

flows these two ciphertexts into the public channel to verify
that the attacker can distinguish between them. The specific
formalization of each algorithm is omitted here, but this is
how confidentiality verification is performed.
5.2.2 For Integrity
To verify the integrity of the AEAD, sub-processes for the
sender and the receiver of the ciphertext are defined, respec-
tively. Then, using correspondence assertions of events, it
is verified that the plaintext encrypted by the sender and
the plaintext obtained by decrypting the ciphertext by the
receiver always match. In this way, AEAD’s security verifi-
cation, including the impersonation, is achieved.

We have reported to Meta via the Meta Bug Bounty [27] on

which is found in this study. The timeline and flow of the

ing that the security model should be extended to take
into account the exploit of revoked devices.
• On October 8, 2024, after discussions of Meta Security

was accepted during the design phase.
• On November 11, 2024, we received permission from
Meta to publish the results of this study.
8. Conclusion
We give the first formal verification of the Labyrinth En-
crypted Message Storage Protocol. While all of the security
claims made by Meta in its specification are satisfied, we
showed that there are specific conditions and attack proce-
dures to break the confidentiality and integrity of the message
obtained by abusing a revoked device.
Remaining problems are a security analysis of client-to-
client message encryption (E2EE) and implementation-level
security analysis in Messenger.
