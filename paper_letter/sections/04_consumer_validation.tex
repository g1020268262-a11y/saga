\section{Consumer-Side Propagation Validation}
\label{sec:consumer-propagation}
\label{sec:evaluation}

The validation asks whether incorrect permission survives the production
consumer checks and reaches token issuance and storage. The controlled
harness drives the Provider \texttt{/access} route and receiver handshake,
including OTK release and consumption. Archived source hashes bind the
matcher, consumers, and token-related cryptographic code to the pinned
upstream baseline.

Signed registration material, local certificates, and in-memory transport
provide fixtures while production cryptographic checks remain active. Both
consumers call the original matcher; wrappers record and return its result
unchanged. Fixtures preset neither authorization decisions nor token state.

\paragraph{Control design.}
Both consumers use identical policies. D/A places specific deny ($-1$) before
wildcard allow ($10$); A/A makes both budgets $10$, and D/D reverses the D/A
order. The letters denote specification and observed implementation decisions,
respectively. A/A tests the permitted-token path, and D/D tests Provider-side
rejection, providing controls with agreeing decisions. Each case ran once
with fresh state and one OTK.

In D/A, Table~\ref{tab:consumer-propagation} confirms that permission from both
production matchers reaches token issuance and \texttt{active\_tokens}
storage despite specification denial. One token is generated, sent, and stored.
A/A also reaches token sending and storage; D/D returns HTTP~403 without OTK
release or state change and never reaches the receiver, so receiver rejection
remains untested.

These observations establish controlled consumer propagation, not application
message acceptance. No application message is sent: a boundary stub intercepts
\texttt{receive\_conversation} before the original handler executes.
