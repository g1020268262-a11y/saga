\section{Consumer-Side Propagation Validation}
\label{sec:consumer-propagation}
\label{sec:evaluation}

\paragraph{Environment.}
At consumer-run revision \texttt{8cc5dd7}, the relevant matcher, Provider,
receiver, and token-cryptography source files are identical to upstream
revision \texttt{7372111}.
The harness drives the production Provider \texttt{/access} route and receiver
handler from matcher evaluation through \texttt{active\_\allowbreak tokens}
storage. Signed registration material, local certificates, and in-memory
transport are used with production cryptographic checks active. Matcher wrappers
call, record, and return the original matcher result; fixtures preset neither
authorization decisions nor the resulting token state. A boundary stub
intercepts the call before the original \texttt{receive\_conversation} executes.

\paragraph{Cases and controls.}
Provider and receiver use identical policies. Divergent D/A places specific deny
($-1$) before wildcard allow ($10$); controls are A/A (both rules allow with
$10$) and D/D (wildcard allow $10$ before specific deny $-1$). Each ran once
with fresh state and one OTK. The labels denote specification/observed
implementation, not Provider/receiver outcomes. A/A reaches token sending and
storage; D/D returns HTTP~403 with no OTK release or state change and never
reaches the receiver, so receiver rejection remains untested.
