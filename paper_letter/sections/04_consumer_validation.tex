\section{Consumer-Side Propagation Validation}
\label{sec:consumer-propagation}
\label{sec:evaluation}

\paragraph{Environment.}
At consumer-run revision \texttt{8cc5dd7}, the relevant matcher, Provider,
receiver, and token-cryptography files are identical to upstream revision
\texttt{7372111}. The harness invokes the production Provider \texttt{/access}
route and receiver handler to exercise matcher evaluation, OTK release and
consumption, token generation and sending, and
\texttt{active\_\allowbreak tokens} storage.
Fixtures provide signed registration material, local certificates, and
in-memory transport; production cryptographic checks remain active. Wrappers
record and return original matcher results; fixtures preset neither authorization
decisions nor resulting token state. After token sending and storage, a boundary
stub intercepts the call before the original
\texttt{receive\_conversation} runs.

\paragraph{Cases and controls.}
Provider and receiver use identical policies. The divergent case places
specific deny ($-1$) before wildcard allow ($10$): the specification denies,
while the production implementation permits. The controls use specific then
wildcard allowances ($10$ each), or wildcard allow ($10$) followed by
specific deny ($-1$).
Each case ran once with fresh state and one OTK. A/A and D/D denote allow/allow
and deny/deny for specification/observed implementation, not Provider/receiver
outcomes. A/A reaches token sending and storage; D/D returns HTTP~403,
releases no OTK, leaves state
unchanged, and never reaches the receiver, so it does not test receiver
rejection.

\paragraph{Result and evidence.}
Table~\ref{tab:consumer-propagation} shows both matchers returning $10$,
followed by OTK release and consumption, then generation, transmission, and
storage of one token in \texttt{active\_tokens}.

The empirical endpoint is token issuance and storage, not message acceptance:
no application message is sent and the original
\texttt{receive\_conversation} is not invoked.
