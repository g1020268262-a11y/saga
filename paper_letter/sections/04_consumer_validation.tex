\section{Consumer-Side Propagation Validation}
\label{sec:consumer-propagation}
\label{sec:evaluation}

\paragraph{Environment.}
At consumer-run revision \texttt{8cc5dd7}, the matcher, Provider, receiver,
and token-cryptography sources match upstream \texttt{7372111}.
The harness executes Provider \texttt{/access} and the receiver handler,
including matcher decisions, OTK release/consumption, token generation/sending,
and \texttt{active\_\allowbreak tokens} storage.
Fixtures seed signed registration material and supply local certificates and
in-memory transport; cryptographic checks remain active. Matcher wrappers
return the original result; fixtures preset neither allow decisions nor
issued-token state. After token sending/storage, a boundary stub intercepts
the call before the original \texttt{receive\_conversation} runs.

\paragraph{Cases and controls.}
Provider and receiver use identical policies. The divergent case places
specific deny ($-1$) before wildcard allow ($10$): the specification denies,
while the production implementation permits. The controls use specific then
wildcard allowances ($10$ each), or wildcard allow ($10$) followed by
specific deny ($-1$).
Each case ran once with fresh state and one OTK. Decision pairs below mean
specification/observed implementation, not Provider/receiver. The allow/allow (A/A)
positive control reaches token sending/storage; the deny/deny (D/D)
Provider-blocking control returns HTTP~403, releases no OTK, leaves state
unchanged, and never reaches the receiver, so it does not test receiver
rejection.

\paragraph{Result and evidence.}
Table~\ref{tab:consumer-propagation} records both matchers returning $10$,
followed by OTK release/consumption and one token's generation, sending,
and storage in \texttt{active\_tokens}.

The empirical endpoint is token issuance/storage, not message acceptance:
no application message is sent and the original
\texttt{receive\_conversation} is not invoked.
