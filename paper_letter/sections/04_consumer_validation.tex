\section{Consumer-Side Propagation Validation}
\label{sec:consumer-propagation}
\label{sec:evaluation}

\paragraph{Purpose.}
This experiment validates the implementation segment of the
authorization-bypass path. It follows the recorded Spec-Deny/Impl-Allow case
through the production Provider and receiver consumers to token issuance and
storage; it does not execute application-message acceptance.

\paragraph{Environment.}
The consumer runs use revision \texttt{8cc5dd7}. At that revision, the relevant
matcher, Provider, receiver, and token-related cryptographic source files are
identical to upstream revision \texttt{7372111}.
The harness drives the production Provider \texttt{/access} route and receiver
handler from matcher evaluation through \texttt{active\_\allowbreak tokens}
storage. The harness supplies signed registration material, local certificates,
and in-memory transport while retaining the production cryptographic checks.
Matcher wrappers invoke the original matcher, record its result, and return that
result unchanged; fixtures preset neither authorization decisions nor the
resulting token state. A boundary stub
intercepts the call before the original \texttt{receive\_conversation} executes.

\paragraph{Cases and controls.}
The Provider and receiver use identical policies. The divergent D/A case places
the specific deny rule ($-1$) before the wildcard-allow rule ($10$). The controls
are A/A (both rules allow with $10$) and D/D (the wildcard-allow rule $10$ before
the specific deny rule $-1$). Each case ran once with fresh state and one OTK.
The first and second letters denote the specification and observed implementation
decisions, respectively, rather than Provider and receiver outcomes. A/A reaches
token sending and storage; D/D returns HTTP~403 with no OTK release or state
change and never reaches the receiver, so receiver rejection remains untested.

\paragraph{Result and evidence.}
Table~\ref{tab:consumer-propagation} shows that both matchers return $10$, the
OTK is released and consumed, and one token is generated, sent, and stored in
\texttt{active\_tokens}. The endpoint excludes message acceptance: no application
message is sent, and the original \texttt{receive\_conversation} is not invoked.
