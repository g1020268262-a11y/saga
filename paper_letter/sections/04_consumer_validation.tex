\section{Consumer-Side Propagation Validation}
\label{sec:consumer-propagation}
\label{sec:evaluation}

\paragraph{Purpose.}
We test whether production consumers propagate matcher decisions to token
issuance/storage, independently of Section~\ref{sec:formalization}.

\paragraph{Environment.}
The harness executes production matcher calls in Provider \texttt{/access} and
the receiver handler, with OTK release/consumption, token generation, and
\texttt{active\_\allowbreak tokens} storage. Fixtures replace registration,
certificate services, and TLS transport. Execution stops only at
\texttt{receive\_conversation}, after token sending and storage.

\paragraph{Cases and controls.}
Provider and receiver use identical policies. The divergent case places
specific deny ($-1$) before wildcard allow ($10$): the specification denies,
while the production implementation permits. The controls use specific then
wildcard allowances ($10$ each), or wildcard allow ($10$) followed by
specific deny ($-1$).
Each case ran once with fresh state and one OTK. The allow/allow (A/A)
positive control reaches token sending/storage; the deny/deny (D/D)
Provider-blocking control returns HTTP~403, releases no OTK, leaves state
unchanged, and never reaches the receiver, so it does not test receiver
rejection.

\paragraph{Result and evidence.}
Table~\ref{tab:consumer-propagation} traces the divergent decision through
production consumers. Both matchers return $10$. The Provider returns
HTTP~200 and releases its OTK; the receiver consumes the OTK, generates and
sends one token, and stores it in \texttt{active\_tokens}.

The empirical endpoint is token issuance/storage, not message acceptance:
no application message is sent. No \texttt{receive\_conversation} logic runs.
Neither \texttt{local\_agent.run}, LLM calls, nor tool execution occurs.
