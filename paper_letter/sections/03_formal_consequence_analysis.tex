\section{Formal Authorization Analysis}
\label{sec:formalization}

\paragraph{Authorization properties and ProVerif queries.}
Token-origin consistency does not establish compliance
with the receiver's intended policy. For a static receiver
policy, the desired authorization condition is
\[
 \mathsf{TokenIssue}(R,I,t)
 \Longrightarrow \mathsf{Allow}_{\mathrm{spec}}(P_R,I),
\]
where $R$ is the receiver and token issuer, $I$ is the
initiator, and $P_R$ is the receiver's contact policy.
$\mathsf{Allow}_{\mathrm{spec}}$ denotes permission under
the intended policy semantics. This condition is neither
an executed ProVerif query nor a proved theorem.

The archived ProVerif 2.05 model evaluates two queries
under a fixed specification-Deny/implementation-Allow
divergence. Query listings use source variables; result
lines abbreviate event parameters.

\noindent\begin{minipage}{\linewidth}
\textbf{Query 1: Message-acceptance reachability.}
\begin{verbatim}
query receiver: bitstring, sender: bitstring,
      tok: bitstring, msg: bitstring;
  event(ChatAccept(receiver,sender,tok,msg)).
\end{verbatim}
\begin{verbatim}
RESULT not event(ChatAccept(...)) is false.
\end{verbatim}
\end{minipage}\par

The false negated-event result establishes that
\texttt{ChatAccept} is reachable in the fixed symbolic
scenario.

\noindent\begin{minipage}{\linewidth}
\textbf{Query 2: Token-origin correspondence.}
\begin{verbatim}
query receiver: bitstring, sender: bitstring,
      tok: bitstring, msg: bitstring;
  event(ChatAccept(receiver,sender,tok,msg))
  ==> event(TokenIssue(receiver,sender,tok)).
\end{verbatim}
\begin{verbatim}
RESULT event(ChatAccept(...))
  ==> event(TokenIssue(...)) is true.
\end{verbatim}
\end{minipage}\par

The verified non-injective correspondence requires
a preceding \texttt{TokenIssue} for the same receiver,
initiator, and encrypted token. Together, the results
show that symbolic message acceptance is reachable
despite intended-policy denial, while token-origin
consistency remains satisfied. The acceptance witness
includes token issuance; no standalone
\texttt{TokenIssue} reachability query was executed.

SAGA's existing authentication and token-secrecy
verification does not establish this authorization
obligation. An archived coverage diagnostic reports
an added authorization correspondence as false because
\texttt{PolicyAllow} is not linked to policy enforcement.
The diagnostic concerns \texttt{Accept}, which denotes
token receipt and verification rather than
\texttt{ChatAccept}. It does not identify the Python
matcher defect.

\paragraph{Scenario and protocol interpretation.}
\label{sec:implementation-mapping}

A bounded bridge compares the archived matcher
observation with an independently evaluated policy
decision, checks source evidence, and instantiates
the verified Deny/Allow decision pair in a fixed
ProVerif scenario. This is scenario reconstruction,
not Python-to-ProVerif refinement.

The symbolic initiator has a valid registered identity,
follows the prescribed peer process, and cannot alter
the receiver's fixed policy. The Provider and
Certificate Authority are trusted, private keys remain
uncompromised, and a private symbolic channel abstracts
authenticated and confidential transport.

In the model, \texttt{TokenIssue}$(R,I,t)$ occurs after
the corresponding \texttt{ActiveToken} entry is stored
and before the token is sent. \texttt{ChatAccept}$(R,I,t,m)$
occurs after message receipt and checks of the sender
identity and the stored receiver, initiator, token,
and sender-key binding.

ProVerif assumes the checked authorization divergence;
it does not execute the Python matcher. The resulting
reachability is conditional on the symbolic model and
its assumptions, not an arbitrary-attacker or deployed
exploit. Controlled implementation validation reaches
token issuance and storage, but does not execute
application-message acceptance.
