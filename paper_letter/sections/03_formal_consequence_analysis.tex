\section{Formal Authorization Analysis}
\label{sec:formalization}

\paragraph{Evidence-linked authorization divergence.}
The matcher inconsistency identified in
Section~\ref{sec:authorization-inconsistency}
produces a concrete authorization divergence:
the intended policy denies the initiator, while
the implementation permits it.

For a fixed receiver policy $P_R$, the intended
authorization requirement is
\[
 \mathsf{TokenIssue}(R,I,t)
 \Longrightarrow
 \mathsf{Allow}_{\mathrm{spec}}(P_R,I),
\]
where $R$ is the receiver and token issuer,
$I$ is the initiator, and $t$ is the encrypted
token. This expresses the desired policy
condition; the executed queries below examine
the consequences of the recorded divergence.

A bounded decision bridge independently evaluates
the recorded policy, checks the archived matcher
observation and source evidence, and instantiates
the verified Deny/Allow decision pair in a fixed
ProVerif scenario. The model represents these
decisions through \texttt{ScenarioSpecDeny}
and \texttt{ScenarioImplAllow}. The Provider and
receiver processes proceed according to the
implementation-side permission, while the
specification-side denial is recorded by
\texttt{SpecIntendedDeny}.

An earlier authorization coverage diagnostic
identified the missing policy-authorization
obligation in SAGA's existing authentication
and token-secrecy verification.

\paragraph{Symbolic authorization consequences.}
The ProVerif model extends the communication
process with token-lifecycle and message-acceptance
events. \texttt{TokenIssue} records issuance
after storing an \texttt{ActiveToken} entry.
\texttt{ChatAccept} records message acceptance
after checking the sender identity, token,
and associated sender-key binding.

The archived ProVerif 2.05 execution evaluates
two queries under the fixed Deny/Allow divergence.
The displayed results abbreviate event parameters.

\noindent\begin{minipage}{\linewidth}
\textbf{Query 1: Message-acceptance reachability.}
\begin{verbatim}
query receiver: bitstring, sender: bitstring,
      tok: bitstring, msg: bitstring;
  event(ChatAccept(receiver,sender,tok,msg)).
\end{verbatim}
\begin{verbatim}
RESULT not event(ChatAccept(...)) is false.
\end{verbatim}
\end{minipage}\par

ProVerif reconstructs an execution reaching\newline
\texttt{ChatAccept}. The archived witness contains
the following event sequence, with $R$ denoting
the receiver and $I$ the denied initiator:

\begin{center}
\small
\begin{tabular}{c}
\texttt{SpecIntendedDeny}$(I,R)$\\
$\downarrow$\\
\texttt{ProviderRelease}$(R,I)$\\
$\downarrow$\\
\texttt{TokenIssue}$(R,I,t)$\\
$\downarrow$\\
\texttt{TokenReceive}$(R,I,t)$\\
$\downarrow$\\
\texttt{ChatAccept}$(R,I,t,m)$
\end{tabular}
\end{center}

The accepting path uses an encrypted token
matching an earlier issuance event. Thus, the
reconstructed symbolic execution demonstrates
that specification-level denial can coexist
with Provider material release, token issuance,
token reception, and message acceptance under
the observed implementation-side permission.

\noindent\begin{minipage}{\linewidth}
\textbf{Query 2: Token-origin correspondence.}
\begin{verbatim}
query receiver: bitstring, sender: bitstring,
      tok: bitstring, msg: bitstring;
  event(ChatAccept(receiver,sender,tok,msg))
  ==> event(TokenIssue(receiver,sender,tok)).
\end{verbatim}
\begin{verbatim}
RESULT event(ChatAccept(...))
  ==> event(TokenIssue(...)) is true.
\end{verbatim}
\end{minipage}\par

The verified non-injective correspondence
establishes that each symbolic message acceptance
has a preceding token issuance for the same
receiver, initiator, and encrypted token.

Together, the reachability witness and verified
correspondence establish the central security
consequence: a receiver may issue a token and
accept a message in the fixed symbolic scenario
despite specification-level denial, while
token-origin consistency remains intact.
The authorization failure arises from the
permission decision rather than token forgery.

The analysis assumes a registered initiator
following the prescribed symbolic process,
a fixed receiver policy, trusted Provider and
Certificate Authority, uncompromised keys,
and authenticated confidential transport.
The ProVerif results characterize this
evidence-linked symbolic scenario; controlled
production-code validation in
Section~\ref{sec:consumer-propagation}
separately establishes propagation to token
issuance and storage.
