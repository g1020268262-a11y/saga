编制日期：2026-10-26。本文档用于审查论文结构与贡献措辞，不是论文正文，也不改变已有模型、实验或结论。

## 1. 写作定位与顺序

**全文按通信授权的执行顺序展开：policy 判定 → OTK 发放与使用 → ACT/token 请求配额执行。** 三项结果围绕同一个问题组织：身份与凭证通过验证之后，用户配置的策略及数量约束是否被各个执行环节正确落实？

本文的对象是 SAGA 个案中的三项执行义务，不提出通用验证框架，也不声称完整重建或证明 SAGA。三项结果分别由不同场景与证据支持；阶段顺序统一叙事，不表示已经复现了串联三项问题的一次端到端攻击。

推荐工作标题：**Policy and Quota Enforcement in SAGA**。

中文释义：**SAGA 中的策略与配额执行分析**。

标题用“执行分析”容纳两类已经有实现依据的问题和一项协议保证边界；不把 OTK 转交预先命名为对原论文 Budget 定义的违反。

## 2. 三项贡献的表述

贡献按正文顺序编号，使用“对象＋发现／分析动作＋结果＋条件”的句式。

**C1：策略判定的一致性。** 识别最具体规则优先语义与实际 matcher 求值之间的次序依赖，确认合法策略配置中的明确拒绝可被较一般的允许规则覆盖，并通过受控消费者执行观察该许可传播至 OTK 释放及 ACT 签发、存储。

**C2：OTK 发放与实际使用的对应关系。** 在保留每发送方领取上限、身份认证与 OTK 单次消费的固定配置模型中，展示获准发送方之间的主动转交可以使领取者与使用者不一致；由此区分 Provider 的发放预算与每身份实际使用数量这一更强目标。

**C3：ACT 请求配额的原子执行。** 将请求限额表述为累计准入数量约束，分析检查与扣减之间的并发交错；用有限 TLC 反例和受控原生方法调用说明余额保持非负仍可能发生超额准入。

这三项贡献是具体发现与分析结果。“使用 Tamarin/TLC”“完成若干查询”以及“多工具组合”均不单独列为创新。与已有工作的差异按具体对象、性质与证据解释，不使用未经查重支持的“首次”“首个”或“全面证明”。

## 4. 逐章大纲

### 1 Introduction｜引言

**主题句：身份认证与凭证有效性不能替代对策略判定、凭证使用对象和请求数量的执行检查。**

段落安排：

1. 用 SAGA 的具体授权流程引出问题：policy 决定接触许可，Provider 发放 OTK，接收方签发 ACT，后续请求受限额约束。避免泛泛铺陈“大模型快速发展”。
2. 用原论文已验证的认证／保密目标定位本次问题，并简要联系凭证绑定和协议保证范围的相关分析。已有证明覆盖什么与本次新增检查什么应分别说明。
3. 按 C1、C2、C3 顺序给出三项贡献，可用一段中的三个短分句；末句强调实现缺陷与模型内保证边界采用不同证据口径。

本章只提出结果，不展开规则代码、全部查询名称或详细实验配置。无需另写长篇章节导航。

### 2 SAGA Workflow and Analysis Scope｜协议流程与分析范围

**主题句：本文沿 SAGA 的策略判定、OTK 建立和 ACT 请求处理三个环节检查不同执行义务。**

先统一符号：P 为 Provider，A 为接收方，B/C 为两个发送方；`CP_A` 为 A 的接触策略；`I(A,C)` 为 Provider 向 C 发放 A 的 OTK 数量；`U(A,C)` 为 C 成功使用的不同 OTK 数量；`Q_t` 为 ACT 的初始请求额度。

图 1 仅展示必要的消息与状态变化：

```text
P 对申请者执行 policy 判定 → P 检查领取配额并发放 OTK
→ A 复核实际连接者的本地 policy → A 检查并消费 OTK
→ DH 与 ACT 签发 → ACT 检查、请求准入和扣减
```

其中接收端再次执行 policy 来自当前实现；不要因为章节主线是 policy → OTK → ACT，就错误地把两端判定合并为实际时序中的一次操作。图中以侧向虚线标出 B 将 OTK 交给 C，并在请求处理处标出并发连接。

随后用一段交代分析分工及范围：

- C1：真实 matcher 与 Provider／接收方的受控执行；策略由用户配置，不假设攻击者可以任意修改他人的策略。
- C2：Tamarin；固定 A、B、C，两个 OTK，B/C 初始领取配额各为 1，静态允许策略及理想 mTLS；主动转交是显式行为，不引入长期私钥泄露。
- C3：TLA+/TLC 与原生方法的受控调用；保留检查与扣减分离及可交错的多个连接，不把原实现直接抽象成原子操作。

这些模型不是相互精化的完整系统证明。正文直接说明假设；完整源码映射、版本、命令和哈希放在随附 artifact。用工具名说明分析手段，不用工具名划分论文的贡献章节。

### 3 Policy Evaluation Consistency｜策略求值一致性

**主题句：当前 matcher 的规则选择状态更新不完整，使应由最具体规则决定的许可依赖规则排列。**

本章采用“预期规则 → 实现机制 → 受控结果 → 精确影响”的顺序。

1. **预期规则。** 只引入本反例需要的最具体规则优先语义。明确拒绝与通配允许同时匹配时，具体拒绝应决定结果。
2. **最小实例。** 两条策略即可：`alice@example.com:* → -1`，`* → 10`。说明已保存的直接调用中，具体拒绝在前时返回 10，反向排列返回 -1。根因是选中规则后未更新 `best_pattern`。
3. **传播证据。** 受控 Provider `/access` 与接收方处理路径使用真实 matcher；规范拒绝／实现允许的配置到达 OTK 释放、消费及 ACT 签发、存储。明确 TLS 连接和注册由 fixtures 替代，应用消息处理没有执行。
4. **对照。** 简述允许路径和拒绝路径均按预期执行；拒绝对照在 Provider 阻断，不能写成观察到了接收端拒绝。

正文结论：**已确认的实现级策略求值分歧及其至凭证签发的受控传播。** 不把它扩大成任意策略的完整正确性证明，也不把已有条件性 ProVerif 消息接受轨迹与上述执行拼成同一次真实通信。

主要证据：`policy-matcher-sanity.json` 和成功的 consumer 归档 `20260926T070021921746Z-d64c8064`；完整定位见《证据与章节对应表》。

### 4 OTK Issuance and Use｜OTK 发放与实际使用

**主题句：按发送方限制 OTK 发放数量，并不自动把该 OTK 的后续使用绑定到领取者。**

本章采用“预算定义 → 待检验关系 → 主动转交执行 → 保证范围”的顺序。

1. **先承认已有规则。** 论文直接定义的是 Provider 的发放计数。在预算不重置的当前配置中，模型保留 `I(A,C) ≤ 1`，该上限仍然成立。
2. **提出候选关系。** 用一行自然语言或简短事件公式说明：`AcceptRequest(A,C,k)` 是否要求此前存在 `ProviderIssue(A,C,k)`？这是更强的领取者／使用者对应关系，不预先写成原论文已经证明的性质。
3. **给出主见证。** C 先合法使用自己的 OTK 并完成请求；Provider 因额度耗尽拒绝其再次领取；B 将另一个已领取、尚未使用的 OTK 转交 C；C 用自己的身份、PAC 与 SAC 取得新 ACT 并完成第二次请求。Provider 仍各发一次，每个 OTK 仍各消费一次。
4. **给出关键对照。** 禁止转交后，B/C 正常流程仍可达，而同人对应关系成立、上述执行不可达。两端拒绝 C 的补充配置不作为主线，因为针对 C 的性质可能空成立。
5. **收紧结论。** 固定配置中 `I(A,C) ≤ 1` 与 `U(A,C) = 2` 可同时出现。该结果揭示发放预算与实际使用上限之间的条件缺口，不表示 Provider 超发、DH 被破解或原文 Budget 的字面定义被违反。

主文只需要发放上限、转交见证、同人对应和正常路径四类检查，不报告“30 项查询”作为研究贡献。论文 C4 威胁能力已经涉及恶意 Agent 之间共享访问控制材料；因此也不能写成“原论文完全没有考虑共享”。

主要证据：Tamarin 模型及最终归档 `run-20261025T033815645931Z`。这里只陈述模型结果；未进行原生网络转交重放。

### 5 ACT Request Quota Enforcement｜ACT 请求配额执行

**主题句：ACT 的剩余余额保持非负，仍不足以保证累计准入数量不超过最初额度。**

本章采用“安全性质 → 原子性缺口 → 模型反例 → 受控原生结果”的顺序。

1. **定义要检查的数量。** 对 ACT t，检查 `N_admit(t) ≤ Q_t`。`remaining ≥ 0` 只限制余额表示，不能排除 `max(0, remaining-1)` 掩盖的超额准入。准入、后端调用和业务任务完成分开记数。
2. **定位源码。** `token_is_valid()` 在锁内检查，后续 `receive_conversation()` 再次加锁扣减；两段临界区之间允许其他连接通过检查。
3. **最小交错。** 余额为 1 时，两个连接先后通过检查，再先后扣减，最终余额为 0，但已有两次准入。用一行四步序列即可，不另加第二张大流程图。
4. **模型结果。** `SagaQuotaDelivery` 的无故障并发配置违反 `ReceiverQuotaSafety`；这是固定 TLC 配置的反例，不是无限连接／任意配置的完整证明。
5. **原生方法对照。** 已保存实验中，额度 50、串行 51 次提交产生 50 次计数后端调用；49 次串行后同时选择最后额度检查的合法交错，总计产生 51 次调用且余额为 0。三次受控重复均如此。传输、证书发现和计数后端有替代，不能写为真实 LLM 或生产网络漏洞复现。

消息中断造成双端余额差额是另一个计账问题，其语义需要明确按发送尝试、接收准入还是业务完成扣费；本 Letter 不把它追加成第四项贡献，以免冲淡当前原子性问题。

主要证据：`concurrent_race` 的 TLC 输出及 `output/analysis/qmax-20261020/results.json`。前者的反例终点是准入超限；后者独立提供方法级调用数量的观察，二者不能合写成一条相同轨迹。

### 6 Discussion and Conclusion｜讨论与结论

**主题句：三项结果分别要求策略求值正确、一次性材料使用对象明确，以及配额检查与扣减保持原子性。**

表 1 用三行合并比较“阶段／检查目标／结果／证据范围”，沿 policy → OTK → ACT 排列：

| 阶段 | 核心结果 | 结论类型 |
|---|---|---|
| policy | 规范拒绝却返回允许，受控传播至 ACT 签发 | 实现级分歧与受控传播 |
| OTK | 发放预算成立，但主动转交破坏同人使用对应 | 固定符号模型中的保证边界 |
| ACT | 有效凭证下并发检查／扣减可产生超额准入 | 有限状态反例与受控原生方法观察 |

讨论限于两点：第一，这些执行义务不能由身份认证和 token 来源真实性代替；第二，修复设计分别指向正确的规则选择、需要时的领取者绑定，以及检查／扣减的原子化。当前没有三项修复后的联合验证，故只给设计启示，不写“我们证明修复后系统安全”。

结论按同一顺序复述三项已支持的结果，用一句话限定为固定版本、所列模型／替代环境和所检查性质下的 SAGA 个案分析。
