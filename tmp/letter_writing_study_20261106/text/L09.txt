1. Introduction
In public key encryption with keyword search (PEKS) [1],
a receiver generates a trapdoor (that corresponds to a search
query) that allows to search a ciphertext encrypted by the
receiver’s public key. A server, that is typically called the
cloud server or the test server, runs theT estalgorithm that
takes a ciphertext and a trapdoor. Since a trapdoor is gener-
atedbythereceiver’ssecretkey,nobody,exceptthereceiver,
should not be able to generate a trapdoor.
Shi, Xu, Cao, and Cheng (SXCC) [2] considered the
following two types of keyword guessing attacks (KGAs).
Oﬄine KGA:Assumethatanadversaryhasatrapdoorand
would like to know which keyword is associated to the
trapdoor. Then, the adversary chooses a keyword, en-
cryptsthekeyword,andrunsthe T estalgorithm. Then,
theadversarycanobtainkeywordinformationfromthe
trapdoor that leaks information of search queries.
Online KGA:Assumethatanadversarygeneratesacipher-
text of a keyword and sends it to the test server (cloud
server). When the server returns the ciphertext against
a receiver’s query (a trapdoor), then the adversary can
decide the trapdoor is associated to the keyword.
The main aim of the SXCC paper is to proposer a PEKS
scheme that defends against both types of KGAs. We call it
the SXCC scheme.

Our Contribution. In this short note, we analyze the se-
curity of the SXCC scheme [2]. Concretely, we show that
a trapdoor can be generated from a ciphertext without using
the receiver’s secret key.
We clarify that our attack violates their security model
becausetheyemployedaslightlyweakersecuritymodel(See
Sect.2). Concretely, an adversary is not allowed to issue an
encryptionqueryforthechallengekeyword. Sinceourattack
converts a ciphertext into a trapdoor, the adversary needs to
obtain a ciphertext of the targeted keyword. Their security
models do not allow for such a query.
Nevertheless, we claim that our analysis indicates that
the scheme must be completely redesigned. For example,
a cloud server that receives a ciphertext from a sender can
generate a trapdoor and execute theT estalgorithm, even
thoughthereceiverdoesnotprovideatrapdoortotheserver.
This situation does not match the roles of the cloud server
in PEKS. More concerningly, if any third party obtains a ci-
phertext, they also can generate a trapdoor. This means that
they can decide whether two ciphertexts are encryption for
the same keyword or not by generating a trapdoor from the
ﬁrst ciphertext and by running theT estalgorithm. This ob-
servationsuggeststhat,intheirscheme,keywordencryption
doesnoteﬀectivelyfulﬁllitsintendedpurpose, highlighting
a potential conceptual oversight that may warrant reconsid-
eration of the design.

4. Attack Complexity
Here, we clarify the complexity in terms of runtime. We
report average execution times over 10,000 runs. Since the
SXCCschemeemployssymmetricpairings,weusethePBC
library†. Forachieving128-bitsecurity,weemployparame-
tersgivenin[8]. Toanalyzeattackcomplexity,alltestswere
run on an Ubuntu 24.04.2 LTS system featuring a RyzenTM
5800X CPU, 128GiB RAM, and 9TB storage. One attack
scenarioinvolvesobtainingtwociphertextsanddetermining
whether they correspond to the same keyword. This is ac-
complished by converting the ﬁrst ciphertext to a trapdoor
andexecutingthe T estalgorithmwiththeconvertedtrapdoor
and the second ciphertext. The total running time for this
processis37.969ms: 20.849msfortrapdoorconversionand
17.119ms for executing theT estalgorithm. Note that run-
ning the Enc algorithm twice takes 59.335ms. Even when
accounting for the encryption time, the overall running time
of our attack is 97.304ms, which is considered reasonably
practical.
