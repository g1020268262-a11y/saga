# 双端配额与交付扩展：本轮结果

本报告只根据本目录原始 TLC 输出与结果 JSON 整理，没有重跑原生代码，也没有真实 TLS 故障注入。

## 结论

新模型没有顺序前缀，从 A、B 相同的初始额度开始，展开本地发送、两端各自扣减、消息收发、有限多轮请求和连接故障。
TLC 找到通信已结束且待处理扣减/帧已清空时的余额差额：第一条请求中断可得到 B=49、A=50；先完成一次普通交互，再中断下一条请求，可得到 B=48、A=49。

这违反的是明确提出的候选终态计账性质，不直接等同于突破 A 的请求次数上限。原接收侧并发超额性质在扩展模型中也单独发现反例。

## 对照结果及其用途

- 正常单连接两轮请求的终态余额一致性检查完成，说明没有把正常在途差额一律判为问题。
- A已准入后的回复中断配置未发现所检查的终态余额差额，且独立查询确认该故障分支可达。因此，B未收到回复不意味着A未处理，不能据此无条件退款。
- 完整请求形成之前的发送错误配置未发现余额差额，独立查询确认该分支可达。它只覆盖这一类发送错误，不能据此判断所有发送异常均未交付。
- 无故障并发配置仍出现 ReceiverQuotaSafety 违反。消息收发过程的展开没有把原来的检查与扣减合并。

## 原生依据与限制

B在 agent.py:513 的发送调用返回后，于518–519行扣减；535–540行接收失败后退出，没有恢复余额。A在586–601行接收、解析和检查，于604–605行另行加锁扣减。
连接中断是新增环境假设。模型没有把普通TCP丢包视为应用消息静默丢失，也没有完整表示TCP/TLS、所有发送异常、部分帧EOF、自动重连或业务重试。
仍需将具体故障轨迹映射到原生执行，并根据按发送尝试、接收准入还是业务完成计数，确定哪些差额应恢复。本轮不宣称真实部署漏洞，不提供退款修复。
