# SAGA 配额验证实施大纲

日期：2026-10-24  
状态：实施前大纲；本轮仅整理计划、核对已有记录，未新建模型或启动验证实验。

## 一、要完成什么

围绕一个明确问题完成验证：**同一个有效 token 的初始配额为 Q 时，接收方 A 是否可能因为并发请求，累计放行超过 Q 个请求？最小原子化修复能否消除这种执行？**

完成后的证据链为：

> 固定版本的原生源码 → 源码与模型的对应关系 → TLC 反例 → 原生代码受控复现 → 修复模型与实现对照 → 可复查的结论。

这条主线验证接收侧的配额执行。Matcher 的访问控制问题独立处理。发送端与接收端计数不一致、异常配额配置等现象保留为单独项目，不把它们自动归为同一种漏洞。

## 三、分阶段实施

### 阶段 1：固定研究对象，定义“超额”

**要做的事：**

1. 固定源代码版本，核对相关文件哈希、运行环境和已有探针的版本。
2. 核对论文中 Q_MAX 的原文定义，记录论文版本、页码和段落；区分论文描述的限制与实现实际计数的事件。
3. 明确角色：A 是诚实执行接收逻辑的目标进程；B 合法持有 token，可以控制自己的客户端并建立多个连接。B 不控制 A，也不需要伪造 token。
4. 以同一次签发、同一个 token 的有效期内为计数范围，明确配额的单位是请求准入，不把“一次通话”直接等同于一个连接或完整业务任务。
5. 分别定义“检查通过”“接收侧配额准入”“后端调用”“业务成功”和“消息交付”。

**核心性质：** `AcceptedCount(t) <= InitialQuota(t)`。其中 `AcceptedCount` 在接收侧通过检查并进入扣减后的处理路径时累计；后端调用单独记录，作为实现中的对应观察。

辅助检查包括余额非负、额度耗尽后不再准入、有效请求正常可达。`remaining >= 0` 单独成立不能说明没有超额，因为实现使用了 `max(0, ...)`。

**产出：** 研究范围、威胁假设、事件定义和性质清单。

**验收：** 能明确判断一条执行在什么位置算作消耗额度、是否超额；不会把客户端改值直接视为接收侧绕过。

### 阶段 2：从源码抽取状态与并发步骤

**要做的事：**

1. 追踪 token 签发、两端存储、接收检查、扣减和后端处理之间的调用关系。
2. 标记 `token_is_valid()` 与后续扣减各自的加锁范围，以及不同连接由不同线程处理的入口。
3. 建立“源码位置—模型变量—模型动作—省略内容”的对应表。
4. 保留原实现的两个步骤：先 `Check`，再 `Consume`。不能在原模型里把它们合并为一个原子动作。

模型至少保留：初始配额、剩余额度、累计准入数，以及每个连接当前所处的步骤。初版使用一个固定、有效、未过期且身份匹配的 token；重启、撤销、网络故障和业务计算不进入第一版状态空间。

**产出：** 源码到模型的映射表、原实现状态转换说明、抽象假设。

**验收：** 每个会影响结论的模型动作都有源码依据；每个被省略的机制都有明确理由。

### 阶段 3：建立最小可运行模型

**要做的事：**

1. 检查 Java、TLC 及所需依赖，记录版本和执行命令。
2. 编写 TLA+ 模型与 TLC 配置。需要时使用 PlusCal 生成 TLA+，但不把 Python 到模型的人工抽象说成自动翻译。
3. 先以小配额、少量连接运行，检查初始化、正常准入、拒绝和终止行为。
4. 检查模型没有因无法发生准入而“空泛通过”；合法结束也不能误报成协议死锁。

**产出：** 可运行的原实现模型、配置文件和运行说明。

**验收：** 串行正常路径可达，耗尽后拒绝可达，模型能通过语法与基础运行检查。

### 阶段 4：用 TLC 搜索并解释原实现反例

**要做的事：**

1. 先检查“配额 1、两个连接”的最小场景。
2. 预期搜索的执行形态为：两个连接先后检查到余额 1，随后分别进入扣减与处理，累计准入 2 次，余额仍为 0。是否存在该执行，以实际工具输出为准。
3. 保留反例原始输出，整理每一步的连接、程序位置、余额和累计准入数。
4. 补充默认配额 50 的检查，或明确建立“先合法使用 49 次，再进入余额 1 的并发后缀”的对应关系，避免只凭 Q=1 就声称已验证默认配置。

注意：原模型中的 `Consume` 不能额外增加“此时余额必须大于 0”的新检查，否则会把真实实现中已经通过检查的第二个请求排除掉。

**产出：** TLC 反例、中文执行表、对应配置与日志。

**验收：** 反例确实违反累计准入上限，且每一步在模型中合法。若未找到反例，先核查模型和假设，不修改性质来迎合预期。

### 阶段 5：把反例对应到原生代码执行

**要做的事：**

1. 复用已有探针中调用原生方法的部分，把 TLC 的关键交错顺序转成受控调度。
2. 在同一个 A、同一个 token、两个持有匹配身份的连接上，分别记录检查通过、扣减、准入和后端调用。
3. 同时运行串行对照，确认结果来自并发交错。
4. 保留调度位置、源文件哈希和日志，说明哪些外围组件被替换。

**产出：** 可复现脚本、结构化结果、模型反例与代码事件的对应表。

**验收：** 在不修改原生配额逻辑的情况下复现对应执行；能解释模型中的每一步在代码中如何发生。受控调度证明该执行可发生，不据此估计其自然发生概率。

### 阶段 6：实现最小修复并建立对照

**要做的事：**

1. 在修复模型中，将检查与额度预留／扣减合并为一个原子动作。
2. 在隔离副本中制作实现补丁，使影响准入的有效性检查和扣减在同一个临界区内完成；后端调用不放进额度锁内。
3. 处理原检查函数内部已经加锁的事实，避免外层持有非重入锁时再次调用它造成死锁。
4. 使用相同的性质、参数和调度，对比原版与修复版。

**产出：** 修复模型、最小实现差异、前后对照结果。

**验收：** 原版出现反例；修复版在所检查范围内不超额；合法请求仍能处理，没有通过拒绝所有请求或阻塞来满足性质。

### 阶段 7：扩展边界与回归检查

**要做的事：**

1. 按状态空间规模安排配额 0、1、2、默认 50，以及单连接、双连接、更多连接的代表性组合；不预先承诺所有参数的全组合搜索。
2. 覆盖额度耗尽、连续请求、多个 token 互不串账等实现对照，并明确哪些场景需要扩展模型。
3. 对原版与修复版使用同一组适用配置，保存完成、失败、超时等实际结果。
4. 将异常配额配置、发送成功但交付失败等现象单独列出；若要继续验证，分别定义输入约束或交付／计费性质，另建模型和实验。

**产出：** 参数与结果矩阵、边界说明、回归记录。

**验收：** 能区分“检查完成且未发现违反”“发现反例”“未完成搜索”；每一项结论能定位到具体配置。

### 阶段 8：整理可复查的验证包

**要做的事：**

1. 汇总版本与哈希、假设、源码映射、原版／修复模型、TLC 配置、反例、复现脚本、补丁及对照结果。
2. 给出从干净环境复查结果的命令与依赖说明。
3. 写明哪些结论由模型支持，哪些由原生受控执行支持，哪些仍待验证。

**产出：** 中文验证报告和统一复现入口。

**验收：** 第三方能够依据说明重跑关键结果；报告不会把有限状态检查写成任意参数定理，也不会把替换传输的实验写成真实部署攻击。

## 四、完成标准与可选增强

本轮验证流程的完成标准是：**性质定义清楚、源码映射可查、原模型反例可重跑、原生执行可对应、修复对照有效、结果范围明确。** 若某一环无法完成，报告应保留缺口，不能用另一类证据替代它。

以下工作可以增强结论，但应单独安排：

- 使用本地真实 TLS、原生连接处理路径重复关键并发场景，增强传输层对应证据；是否还替换 Provider、证书发现或 LLM，应分别标明。
- 对任意非负初始配额和任意连接数量证明修复不变量；这需要额外证明工作，有限 TLC 搜索不能替代。
- 为消息丢失、重试、崩溃恢复定义额度扣减与交付语义，分析两端计数一致性。

执行顺序：阶段 1–2 明确对象和映射 → 阶段 3–4 得到模型与实际搜索结果 → 阶段 5 对应原生执行 → 阶段 6–7 完成修复和边界对照 → 阶段 8 归档报告。
