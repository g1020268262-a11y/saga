# SAGA 原生 Q_MAX 设置与执行机制分析

核查日期：2026-10-20。原生版本：`7372111bea150e32cee390a616849316d2780bfc`。

结论：固定设置 `Q_MAX = 50`、保持 token 密文不变并维护本地剩余计数，本身并不构成越权漏洞。但原生接收端将配额校验与扣减分离，存在可由同一合法 token 的并发请求触发的额度超支。在受控调度下，额度 50 对应了 51 次真实的原生后端调用入口。另有初始额度未绑定外部认证上限、双端计数可能失步、配置缺少校验等边界，不能把它们全部等同于未经授权的远程访问。

## 原文语义与实现对应

论文 v2 第 8 页 §IV-E 第 7–8 步将 Q_max 定义为与一个 token 绑定的请求数量上限，由接收请求的 A 生成 token，发起方 B 持 token 请求 A。A 应检查身份绑定、有效期和额度。Token 可在连接重建后复用，因此额度是每个 token 的限制。

原文：https://arxiv.org/html/2504.21034v2#S4.SS5

实现中的 `saga.config.Q_MAX` 是签发初始值；`active_tokens[token]["communication_quota"]` 是 A 的剩余额度；`received_tokens[token]["communication_quota"]` 是 B 的本地副本。token 密文并不随扣减重新生成。正常串行处理下，A 的本地账本能够阻止 B 仅修改自身副本或重造 token 来增加请求额度。

## 1. 已复现：并发请求可超出同一个 token 的请求额度

相关原生位置：`saga/agent.py:348–381`、`597–605`、`1180`。

A 在 `token_is_valid()` 中加锁检查，函数返回时释放锁；之后 `receive_conversation()` 再次加锁扣减。这不是一个原子操作。接收服务为每个连接启动线程，也没有限制某个 token 只能有一个活动连接。

剩余一次额度时，合法调度如下：

| 顺序 | 连接线程 1 | 连接线程 2 | A 的剩余额度 |
| --- | --- | --- | --- |
| 1 | 原生校验通过，释放检查锁 | | 1 |
| 2 | | 原生校验通过，释放检查锁 | 1 |
| 3 | 获取扣减锁，扣减并继续处理 | | 0 |
| 4 | | 获取扣减锁，执行 max(0, 0 - 1)，继续处理 | 0 |

两个请求都会到达 `local_agent.run()`。`max(0, ...)` 只避免负数，不能撤销第二次放行。将校验改为 `<= 0` 而不合并检查与扣减，也不能消除这一竞态。

执行结果：

| 场景 | 原生后端调用次数 | 最终剩余额度 |
| --- | ---: | ---: |
| 默认额度 50，串行提交 51 条请求 | 50 | 0 |
| 默认额度 50，先串行处理 49 条，再并发提交两条 | 51 | 0 |

并发场景重复三次，全部为 51 次。两个连接都运行原生连接处理函数，使用同一 B 的真实本地证书、Provider 签名和 PAC，使用同一合法 token；原生身份验证没有被替换，matcher 使用简单允许规则，不依赖 matcher 顺序问题。

攻击者所需能力：控制一个有权联系 A、已获得合法 token 的 B，使用自己的身份和 token 建立多个连接，并发发送请求。无需更改 A 的配置、伪造 token 或获得其他 agent 的私钥。探针通过 Python trace barrier 选择“两个检查都完成、尚未扣减”的合法调度，不修改授权判断或扣减语句。

已证实的是原生方法在受控调度下的额度超支和额外后端调用。没有测量真实网络中自然触发的概率、最大放大量、实际 LLM 费用或业务数据影响。

## 2. 设计边界：初始额度由 A 配置，尚不足以单独认定越权

相关位置：`saga/config.py:75`、`saga/agent.py:321`、`383–413`、`871–874`。

原生签发函数直接使用本地 `Q_MAX`，没有从用户签名的 per-agent/per-peer 请求额度策略或 Provider 的额度授权中派生这个值。B 接收 token 后也没有把其初始额度与本地 Q_MAX 或一个经认证的上限比较。

论文 §II-A Definition 1 将 user 定义为 agent 的所有者及任务委托者。因此，A 的所有者正常调整自己服务授予 B 的额度，属于其管理权限。论文没有另外定义一个不可被该所有者调整的、由 Provider 统一制定的每 token 请求上限。不能把一个额外设想的授权要求直接当作原协议已经承诺但违反的保证。

B 本地的 Q_MAX 用于 B 作为接收方签发自己的 token，并不自动表达 B 作为发起方愿意承受的最大工作量。若需要限制 B 自身的外发请求、LLM 费用等，应另设清晰的本地任务预算。

控制实验：A 在签发时配置为 999，随后恢复配置为 50；B 在本地 Q_MAX 为 50 时仍保存额度 999，并判定 token 有效。这表示其初始额度被接受，不表示一个连接能完成 999 次请求，因为代码还存在独立的 `MAX_QUERIES` 循环限制。

安全含义取决于要求：

- 如果 A 代表资源所有者，有权决定授予 B 多少额度，这属于本地配置策略，不能单独称为越权。
- 如果要求用户或 Provider 规定的请求次数上限不可被 agent 擅自扩大，现实现没有建立这样的参数授权绑定。
- 签名授权参数可以限制未获授权的参数变更，但不能强迫一个完全被攻击者控制的 A 进程诚实执行本地计数。

此处“完全控制”是分析时明确增加的能力前提：攻击者能修改 A 的程序、配置或进程内存，例如直接改变 active_tokens。它不指所有者正常管理，也不等于普通提示词影响。论文 §III-D C2 允许 agent 被攻陷，但未把每一种提示注入都具体等同于任意进程内存写权限。本次没有构造或验证从提示注入到修改额度的攻击链。

Provider 的 contact-policy budget 是 OTK 发放次数，不能直接当作单个 token 的 Q_MAX。固定每个 token 50 次也不等于 A、B 之间永久只能请求 50 次；获得新 OTK 并签发新 token 后，会有新的 token 额度。这是论文允许的续用设计。

## 3. 条件性失步风险：传输替代实验不等于真实网络故障复现

相关位置：`saga/agent.py:513–519`、`586–605`。

B 在本地 sendall 完成后即扣减；A 则在收到并验证消息后扣减。两者之间没有应用层的额度确认与恢复协议。

探针模拟“B 本地写入成功，但未向 A 交付请求”：B 剩余 49，A 仍剩余 50。该控制场景只验证这个前提下的原生扣减结果，没有证明真实 TLS 连接中自然触发该前提的概率，也不等于一次真实网络故障实验。

需要区分几个时点。B 扣减后 A 尚未处理时，49/50 可能只是正常的短暂差异；随后 A 收到并验证请求，就会变成 49/49。只有通信最终失败、A 没有接受该请求且没有恢复机制时，才留下持久差异。普通丢包通常由 TCP 重传，不能直接当作额度永久失步的充分条件。

另外，“A 已处理请求，但回复丢失”时，两边可能已经都是 49，问题是 B 不知道业务是否执行成功，并非计数必然不一致。发送接口报错时也不能仅凭客户端错误推断 A 一定没有收到完整请求。

这主要会使正常 B 提前停止、浪费其可用额度，不能据此推导 B 绕过 A 的配额。消息已经被 A 处理但响应丢失后的应用重试，也不能仅凭现代码认定为按唯一业务请求精确计费。

论文要求 A 执行每 token 的使用上限，没有明确规定双端余额在任何故障时都必须相同。因此，该点目前应描述为待验证的故障恢复/可用性问题，尚不能认定为原协议限额安全保证已被突破。若要求可靠恢复，应先明确按发送尝试、A 接受的请求还是唯一业务请求计数，再设计请求标识、A 的原子记账、应用层确认以及重试去重，不能仅把 B 的扣减移动到收到回复后就认为问题解决。

## 4. 已核实：配置缺少有效性检查

原生代码只判断 `remaining_quota == 0`，签发入口没有要求 Q_MAX 为合法的非负整数。设置为 -1 后，原生校验先放行一条请求，再由扣减语句夹到 0；探针记录一次后端调用。

这属于配置鲁棒性问题，前提是配置被误设或被能修改本地配置的人修改；默认值 50 本身不会触发该行为。它不是无限请求绕过。

## 5. 不应误判的现象

- 仅修改 B 自己的剩余额度为 999：串行对照中 A 仍只处理 50 条请求。
- 使用共享密钥重新加密一个新 token：A 找不到完全相同的已签发 token 字符串，因此拒绝。
- A 改大自己的本地余额：不会自动同步增加正常 B 的本地余额。
- token 中的初始额度没有递减：原生设计使用有状态的本地账本，这件事本身不是漏洞。
- 限制请求条数：不等于限制请求速率、总输入 token、工具执行次数或计算费用。单条请求对应多少工作，由后端另外决定。

## 修复优先级

1. 将 A 的 token 存在性、有效期、PAC 绑定、余额判断和额度预留放在同一个临界区，余额不足立即拒绝，成功预留后再释放锁并执行业务。保留请求唯一性时还需单独定义重试语义。
2. 在签发入口验证额度类型与取值；无效配置直接拒绝，接收路径采用防御性的非正数检查。仅改变比较符号不能修复并发竞态。
3. 明确额度究竟由资源所有者本地决定，还是必须服从用户/Provider 的认证策略；后者需要把初始额度及其策略来源绑定起来。
4. 若双端余额需要一致，定义消息标识、确认、重试和恢复流程；若不要求一致，应明确 A 是放行的权威账本，B 的副本只用于本地控制。
